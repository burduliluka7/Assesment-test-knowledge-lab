## A3. Semantic similarity is candidate generation, not proof of identity

If lexical matching does not resolve the target, semantic similarity may generate candidate nodes using the contextual graph representations defined later.

However:

```text
semantic similarity alone MUST NOT be sufficient
to classify a candidate as ALIAS_NODE.
```

A high embedding similarity means:

```text
"possibly related"
```

not:

```text
"definitely the same scientific entity."
```

To accept `ALIAS_NODE`, require at least one independent identity/coreference signal such as:

```text
identifier/name overlap
acronym expansion compatibility
canonical-name containment
repeated explicit use of the short name in adjacent claims
article/title provenance linking the names
version-family evidence
another graph-derived coreference signal
```

If semantic evidence is strong but entity identity is not established, prefer:

```text
EVIDENCE_BACKED
AMBIGUOUS
UNRESOLVED
```

instead of forcing an alias.

# PART B — RETRIEVAL ENTITY GROUPING / SAFE DEDUPLICATION

The graph intentionally contains heterogeneous representations of the same named scientific concept.

A scientific name may appear as:

```text
method
component
dataset
cited_work
article
```

and therefore several nearly identical graph nodes may occupy several top-k positions.

This can significantly damage multi-answer retrieval.

Introduce a query-independent retrieval abstraction such as:

```python
EntityGroup(
    canonical_display_name=...,
    member_node_ids=[...],
    member_types=[...],
    provenance=[...]
)
```

or equivalent.

This is a retrieval/evaluation layer only.

DO NOT modify or collapse the actual TKH graph.

Group only safely equivalent entities using conservative identity rules such as:

```text
identical normalized names
clearly established aliases
```

Do not fuzzy-merge semantically related but distinct methods.

Ranking output should preferably contain one result per scientific entity group rather than multiple identical-name nodes occupying top-k.

Preserve underlying node IDs so evidence traversal can still use the full graph.

Add an ablation:

```text
context retrieval without grouping
context retrieval with grouping
```

to measure whether duplicate heterogeneous nodes were consuming answer slots.

# PART C — CONTEXTUAL GRAPH REPRESENTATIONS

The current retriever should no longer rely mainly on:

```text
"method: MACE"
"dataset: Matbench"
```

or similar short surface forms.

However, DO NOT simply concatenate an enormous neighborhood into one giant string and embed it once.

The graph contains broad heterogeneous relations and some nodes have many neighbors. A giant context document risks semantic dilution and irrelevant co-member contamination.

Use relation-aware, multi-field representations.

For each searchable entity/node/group construct fields such as:

```text
name
type
article/title/provenance
claims
tasks
problems
techniques
components
datasets/evaluations
cited works
selected extension/base-method context
```

Conceptually:

```python
NodeRetrievalRepresentation(
    name_text=...,
    article_texts=[...],
    claim_texts=[...],
    task_texts=[...],
    problem_texts=[...],
    technique_texts=[...],
    component_texts=[...],
    dataset_texts=[...],
)
```

Store vectors separately where practical:

```text
name_vector
article vectors
claim vectors
task vectors
problem vectors
technique vectors
component vectors
dataset vectors
```

This allows the query to strongly match one useful claim/task without that evidence being diluted inside an enormous concatenated paragraph.

## C1. Relation-aware extraction

Do not treat every 1-hop graph co-member as equally useful.

For method-like entities, relations such as:

```text

solves

```

are generally strong contextual evidence.

Relations such as broad:

```text

```

may contain many co-members and should be treated more cautiously.

Do not blindly add the names of every member of a large hyperedge to every other member's retrieval representation.

Preserve direction/role information where available.

For example:


If 2-hop context is used, expose it as an ablation.

# PART H — MULTI-FIELD SCORING

Because representations are multi-field, compute interpretable field scores.

For example:

```text
name_score
claim_score
task_score
problem_score
technique_score
component_score
dataset_score
article_score
type_score
temporal_score
```

For fields with multiple vectors, use a robust aggregation such as:

```text
max similarity
mean of top-m similarities
softmax/top-m pooling
```

Make the choice configurable.

A possible deterministic scorer is conceptually:

```python
final_score = (
    w_name * name_score
    + w_claim * claim_score
    + w_task_problem * task_problem_score
    + w_technical * technical_context_score
    + w_dataset * dataset_score
    + w_article * article_score
    + w_type * type_score
    + w_temporal * temporal_score
)
```

Do not copy these exact weights blindly.

Expose defaults in configuration.

Avoid double counting.

For example, if `semantic_score` already embeds claims/tasks in a giant combined document, do not add the same claim/task evidence again as independent terms.

The reason for multi-field representation is partly to make contributions explicit.

Output score decomposition for every returned result.

Do not keep adding complexity merely because a benchmark metric remains low.

Use this debugging order:

```text

→ candidate eligibility
→ entity deduplication
→ contextual representation
→ query representation
→ reranking
→ hierarchy search
```
